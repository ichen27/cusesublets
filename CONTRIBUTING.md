# Contributing and reporting issues

Use the README's isolated synthetic-data quickstart. Never run mutation tests against a hosted preview or a shared operational datastore. Keep credentials, account cookies, private documents and room captures out of commits and issue reports.

Open a focused feature/fix branch and a pull request. Explain the problem, resulting behavior, validation and remaining limitations. Run TypeScript checks, unit tests and the production build; run affected API checks against fresh local migrations. Native changes also require the iPhone workflow. A compile is not evidence of physical camera behavior.

Preserve user work and migration history. Do not force-push shared branches. The deployment runbook governs operational changes: a watched checkout can change a running service before a commit is pushed. CI success does not authorize a database cutover.

Report technical issues through the GitHub issue tracker with reproduction steps, expected/actual behavior and sanitized logs. Use in-app reports for private abuse concerns. Never put account details, private conversations, identity evidence or room imagery in public issues. A private support channel is a release prerequisite.

No open-source license is currently granted for original project material. Discuss licensing and contribution terms with the owner before external contributions or redistribution.
