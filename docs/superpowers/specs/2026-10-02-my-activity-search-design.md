# CuseSublets: My activity and two-sided discovery

**Design status:** ready for Ivan's review, October 2, 2026. This document describes a proposed change; the current site still uses repeatable seeker requests and a My listings tab.

## Intent and success criteria

CuseSublets should help a person find a sublet, offer one, or do both from the same account. Ivan chose the compact marketplace layout in concept A, with filters beside a mixed Browse feed and a useful map. A seeker should turn on one profile-linked housing search instead of posting repeated requests. They set a price range, rooms, dates, housing conditions, and several desired geographic areas. When someone zooms or pans the map, the People results should reflect who wants to live in the visible area. Top Matches must work for both seekers and hosts and explain each fit. **My activity** replaces **My listings** as the account's operational home for editing subleases and the housing search.

Success means a signed-in member can publish a listing and activate a housing search simultaneously; anonymous visitors can browse the public parts of both; map filtering and matching use the same area and housing rules; and a member cannot create multiple public seeker entries by editing or toggling their search.

## Navigation and page structure

- Desktop primary navigation: **Browse**, **Top matches**, **Inbox**, **Saved**, **My activity**. The account avatar opens personal profile settings and public-profile access. **Apartments** becomes the **Places** filter and map view inside Browse. Keep a **List your place** shortcut that opens the listing flow.
- Mobile bottom navigation contains the same five destinations. The account avatar remains in the header. The map opens from a visible **Map** control on Browse and Matches; returning to List keeps filters and viewport.
- Browse starts with compact search controls, side filters on desktop (a filter drawer on mobile), and **All / Places / People** filters. Cards for places and people have distinct layouts. The large marketing hero and repeated landing-page treatment leave this view. A **Turn on your search** shortcut goes to **My activity → My search**; it is not a separate posting flow.
- My activity has **My subleases** and **My search** sections. My subleases shows every owned listing with its true publication/review state and actions to post, edit, publish or pause as allowed by existing rules. My search shows an on/off control, criteria, chosen areas, and Edit. Both sections can be active at once. The public profile shows **Offering a place** when an approved listing is live and **Looking for a place** when the search is active. Personal details, photos, and identity checks stay in Profile; Inbox stays separate.
- The Top Matches page shows a search summary and matching apartments when the member's search is on. A member with published listings can select a listing and see matching people. If both activities exist, a clear **For my search / For my listing** switch exposes both. Empty states link to the corresponding My activity setup.

## One persistent housing search

Each account has at most one current housing search record. Its stable ID is reused for edits and visibility changes. Required setup fields are stay start/end, monthly maximum, room type, and at least one desired map area. Optional fields are monthly minimum, minimum bedrooms for entire-place searches, required amenities/conditions, preferred amenities/conditions, and a short public introduction. The minimum and maximum form an inclusive price range when both are set. The UI explains that criteria and the introduction are public when the search is on, while account email, phone, identity documents, and private profile fields remain private.

The search is either **on**, **off**, or **removed by staff**. Turning it on requires valid dates, criteria, and at least one area; an incomplete search opens the setup form. Saving edits does not change its original discovery order. Turning it off immediately removes it from public Browse, public profile search details, and both directions of Top Matches. Turning it back on restores the same record without creating a fresh entry or bumping it to the top. If its stay end date passes, it becomes invisible until the member updates the dates. A staff-removed search cannot be reactivated by its owner; staff restoration returns it to **off** so the owner can review it before turning it on. Existing report and audit controls continue to apply. The member can offer listings regardless of search state.

Offering status follows published listings: it is active when at least one owned listing is publicly available. A listing's publication, pause, checks, and evidence rules remain independent. My activity controls each listing; there is no status switch that claims someone is offering a place without a live listing.

## Map areas and Browse behavior

The first release uses user-highlighted map regions, without relying on a third-party neighborhood boundary catalog. The member can add one to five areas by tapping polygon points on the map and closing the shape. **Add visible area** captures the current viewport as a rectangular area and provides a simpler mobile and keyboard path. Members can name, inspect, remove, and redraw each area. The form offers a text list of selected areas alongside the map. The server validates coordinates, area count, polygon shape, and the Syracuse service envelope; it rejects malformed or self-intersecting areas. Map art in the earlier concepts is illustrative, not an authoritative neighborhood boundary or a person's residence.

Places mode shows approximate listing pins. The current behavior where panning/zooming filters the list to the visible map area remains. For a signed-in seeker, their selected areas appear as translucent overlays; listings within any selected region can be emphasized. People mode shows *desired regions*, never pins for a person's present address. A person appears once in the list when any of their selected regions intersects the visible map viewport. Panning or zooming updates the list after the map settles. Selecting a person card highlights only that person's desired regions. On small screens, the Map/List switch preserves the same bounds and filters. The public People cards link to profiles and show only public housing criteria and an optional introduction.

## Matching rules

Use one shared housing-fit function in both directions. A listing is eligible for a search when it is published, its availability covers the full requested stay, its rent is within the search's stated range, its room type is compatible, its approximate listing point lies within at least one selected area, and it provides every required condition. Minimum bedrooms applies when the member seeks an entire place; private-room searches use room type instead. An owner cannot match their own listing. Suspended users, paused/expired/removed searches, and unavailable listings are excluded.

Eligible pairs are ranked by preferred-condition overlap, then lower rent within the selected range, then stable listing/search ID order. The UI uses short **Why it fits** reasons such as area, dates, budget, bedrooms, and requested conditions; it does not show a pseudo-precise compatibility percentage. The seeker sees matching listing cards and pins within selected areas. A host chooses one owned live listing and sees profile cards for people whose selected areas include that listing; the map may shade their desired regions around the listing pin. Contact remains sign-in gated and opens a listing-anchored conversation with search context. Identity status and demographic/profile traits are not matching inputs.

## Data and API transition

Preserve `seeker_requests` IDs because conversations, reports, and audit history refer to them. Add a marker for the one canonical profile-search row per owner, with a database unique constraint on that marker and owner ID. A migration chooses one existing row per owner, preferring their newest active request, then newest other nonremoved request, then newest removed request. It marks that row canonical, carries forward its existing criteria, and pauses every formerly active request. A migrated search remains off until its owner reviews the new fields, selects map areas, and explicitly turns it on. The migration never deletes rows or conversation references. Other legacy rows remain historical and do not appear in public Browse or new matches. A removed canonical row remains blocked until staff restores it. Existing hosted state must be backed up and migrated while its service is stopped; demo state is migrated separately and never seeded into hosted state.

Expose an owner-only **My search** read/upsert/visibility API and a public active-search projection. Existing request GET URLs can remain read-compatible during transition, returning only active canonical searches. Legacy request POST routes stop creating or editing repeatable posts and return an explicit migration error; all new writes use the canonical-search API. All writes require the existing session, same-origin, and ownership checks. Public profile reads include at most one active search summary. Browse and matches fetch only active canonical searches. Admin reports and removal/restoration keep their record IDs and audit history. Contact creation still attaches the canonical search ID to the conversation and verifies both participants and housing fit server-side.

Split implementation responsibilities rather than growing the current large `App` and `Discovery` components: My activity owns member controls; search setup owns form/map editing; Browse owns mixed discovery and viewport filters; a shared geo-and-fit module owns area intersection and matching; Worker routes own validation, authorization, and public projections.

## Verification and rollout

Tests cover one canonical search per account, edit/toggle without duplicate or feed bump, migration with multiple legacy requests and existing conversations, owner reactivation after adding areas, removed-search moderation, public/private field boundaries, map polygon validation and viewport intersection, listing-point inclusion, both matching directions, required versus preferred conditions, bedrooms, dates, prices, and contact authorization. Browser checks cover desktop and narrow mobile navigation, My activity with both roles active, area selection, map/list filtering, matching reasons, and empty states. Run project typecheck, unit tests, build, isolated runtime tests, and hosted guards. Push the feature branch and pass GitHub Checks before advancing main. Back up the exact demo and hosted persistence directories separately, stop each service for its migration, rebuild, restart, and verify both UI and APIs without applying demo seeds to hosted data.

## Scope limits

This change does not add notifications, a new payment or signing flow, exact-address disclosure, identity-based ranking, a neighborhood-boundary data provider, or a separate seeker-post feed. Existing messaging, offers, reviews, checks, and admin permissions remain governed by their current rules except where the canonical housing search must be recognized.
